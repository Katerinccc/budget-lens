# 0009 — Protobuf code generation with Buf and ts-proto

- **Status:** Accepted
- **Date:** 2026-10-12

## Context
ADR 0007 makes `protos/` the single source of truth for the BFF ↔ Api contract. The .NET side
already generates C# at build time through `Grpc.Tools`. The BFF needs TypeScript types generated
from the same files, reproducibly on every developer machine (Windows included) and in CI,
without asking anyone to install `protoc` by hand.

## Decision
- Use **Buf** (`@bufbuild/buf`, an npm devDependency of the BFF) to drive code generation, with
  the **ts-proto** plugin (also an npm devDependency). `npm ci` installs everything needed.
- `protos/buf.yaml` declares the Buf module and its lint (`STANDARD`) and breaking-change (`FILE`)
  rules. `src/bff/buf.gen.yaml` holds the TypeScript generation settings.
- ts-proto options: `nestJs=true` (interfaces and decorators for `@nestjs/microservices`),
  `forceLong=string` (64-bit integers never lose precision), `importSuffix=.js` (ES modules with
  `nodenext` resolution) and `esModuleInterop=true`.
- Generated code goes to `src/bff/src/generated/`, is **gitignored** and is regenerated by
  `npm run proto:gen`, which runs automatically before build, test and `start:dev`.
- CI runs `buf lint` on `protos/` in the BFF job.

## Alternatives considered
- **`protoc` + `grpc-tools` npm package:** works, but needs longer command lines and gives no lint
  or breaking-change detection.
- **`@grpc/proto-loader` at runtime only:** no compile-time types, so contract drift would only
  show up at runtime, which defeats the purpose of ADR 0007.
- **Committing generated code:** visible in reviews, but generated diffs add noise and can go
  stale if someone forgets to regenerate.

## Consequences
- A fresh clone works with `npm ci` and any npm script; no global tools needed.
- `buf breaking` can later be added to CI to block incompatible changes (renumbered or reused
  fields) against `main`.
- Generated files are not visible in PRs; reviewers review the `.proto` changes instead.
